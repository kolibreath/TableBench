# 检查统计后端 · 接口契约与表结构建议

> 对接方：项目管理工具箱插件（估算检查端） ↔ 统计后端（GaussDB）
> 依据：《数据库设计文档_优化版 v2.0》（2026-09-10）
> 插件侧口径：**按规则聚合上报**（不逐条报违例明细），明细以插件本地留痕为准

---

## 一、上报接口契约（请后端按此实现）

```
POST {statsEndpoint}
Content-Type: application/json
```

`statsEndpoint` 由插件侧配置（localStorage `statsEndpoint`，如 `http://<host>:<port>/api/check_records`）。未配置时插件不上报。

### 请求体

```json
{
  "record": {
    "fp_total": 0,
    "must_count": 4,
    "suggest_count": 2,
    "over_estimate": 0,
    "under_estimate": 0,
    "ai_review_count": 3,
    "match_count": 0,
    "unmatch_count": 0,
    "project_no": "XRK2026001",
    "project_name": "新一代核心账务系统升级",
    "source": "ita",
    "rule_version": "v2.0.16",
    "ai_enabled": 1,
    "duration_sec": 12.3,
    "checker_id": "wangyuxiangyf",
    "client_time": "2026-09-11T15:20:00.000Z"
  },
  "violations": [
    { "rule_id": "R5", "rule_name": "…", "type": "强制", "sheet": "SDC202601_0101、SDC202601_0102", "hit_count": 3 },
    { "rule_id": "R8", "rule_name": "…", "type": "建议", "sheet": "SDC202601_0101", "hit_count": 1 }
  ],
  "files": [
    { "file_type": "book",    "file_name": "…_规模估算书_v2.3.xlsx", "file_ext": "xlsx", "batch_order": 1 },
    { "file_type": "require", "file_name": "…业务需求书part1.docx",  "file_ext": "docx", "batch_order": 2 }
  ]
}
```

### 字段说明与口径

| 字段 | 口径 |
|---|---|
| `record.fp_total` | 暂以违例总数占位（功能点总数待检查流程暴露后补充），后端暂勿用于分母计算 |
| `record.over/under_estimate`、`match/unmatch_count` | 暂恒 0；AI 对比统计接入后补 |
| `record.ai_enabled` | 1 = 该次检查配置了 AI 后端；`ai_review_count` 为 AI 实际审核条目数 |
| `record.checker_id` | ITA 登录态 cookie 的 `userId`（域账号）；取不到为空串 |
| `record.client_time` | 插件端检查完成时间（ISO 8601）；服务端 `created_at` 以入库时刻为准，两者可对照时差 |
| `violations[].hit_count` | 该规则本次命中的**条数**（同规则多条违例压缩为一条上报后的计数）；`sheet` 为多 sheet 去重拼接（「、」分隔，截 64 字符） |
| `files[].file_type` | `book`=规模估算书；`require`=需求说明书 |

### 响应

`2xx` 即视为成功；非 2xx 或网络失败插件**静默丢弃**（不重试，本地留痕不受影响）。后续如需补传机制再协商。

### 事务与幂等

插件可能偶发重复上报（如用户在结果页重复触发）。建议后端以 `idempotency_key`（见下节）或 `(project_no, checker_id, client_time)` 建唯一约束做幂等，重复上报覆盖或忽略。

## 二、表结构修改建议（在 v2.0 基础上的最小增量）

### 2.1 `check_record` 增加业务维度列（本轮必须）

没有这些列，数据无法回答「谁、何时、检查了哪个项目、用什么规则版本」：

```sql
ALTER TABLE check_record ADD COLUMN project_no    VARCHAR(64);
ALTER TABLE check_record ADD COLUMN project_name  VARCHAR(255);
ALTER TABLE check_record ADD COLUMN source        VARCHAR(8)  NOT NULL DEFAULT 'manual'
                  CHECK (source IN ('ita', 'manual'));
ALTER TABLE check_record ADD COLUMN rule_version  VARCHAR(16);
ALTER TABLE check_record ADD COLUMN ai_enabled    INT         NOT NULL DEFAULT 0;
ALTER TABLE check_record ADD COLUMN duration_sec  NUMERIC(8,1);
ALTER TABLE check_record ADD COLUMN checker_id    VARCHAR(64);
ALTER TABLE check_record ADD COLUMN client_time   TIMESTAMP;
CREATE INDEX idx_record_checker ON check_record (checker_id, created_at DESC);
CREATE INDEX idx_record_project ON check_record (project_no);
```

### 2.2 `check_violation` 聚合口径的配套（本轮必须）

插件按「规则聚合」上报后，`(check_id, rule_id) UNIQUE` 恰好匹配；但需要**数量列**承载 hit_count，否则「某规则命中次数」语义丢失：

```sql
ALTER TABLE check_violation ADD COLUMN hit_count INT NOT NULL DEFAULT 1;
-- 建议放宽 sheet 长度（多 sheet 拼接）：
ALTER TABLE check_violation ALTER COLUMN sheet TYPE VARCHAR(255);
```

> 后续若升级为明细级上报（每条违例一行），需去掉 UNIQUE、增加 `row / col / message` 列——已在沟通中，暂不实施。

### 2.3 幂等键（建议）

```sql
ALTER TABLE check_record ADD COLUMN idempotency_key VARCHAR(80);
ALTER TABLE check_record ADD CONSTRAINT uk_record_idem UNIQUE (idempotency_key);
-- 插件将在下一版本生成并上报该键（checker_id + client_time 哈希）
```

### 2.4 保持不变的项

v2.0 的索引策略、`ON DELETE CASCADE`、`CHECK` 约束、注释规范均保留，不再重复。

## 三、插件侧行为说明

| 项 | 行为 |
|---|---|
| 上报时机 | 每次估算检查完成后（结果页渲染同时），异步 fire-and-forget |
| 失败处理 | 静默（console.warn），不重试、不影响本地留痕与结果展示 |
| 配置方式 | 浏览器控制台执行 `localStorage.setItem('statsEndpoint', 'http://…')` 后生效；删除该键即停报 |
| 关闭上报 | 不配置 endpoint 即完全不上报 |
| 隐私边界 | 只上报统计与违例摘要（规则号/sheet/计数），**不含文档内容与违例定位明细**；明细仅存插件本地 |
